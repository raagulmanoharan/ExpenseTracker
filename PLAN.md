## Phase 1: Production Hardening (baseline — do first)

### 1. Fix `buildWeeklyDigest` crash
- **Problem:** `buildWeeklyDigest` is imported in `server.js:14` but never defined or exported from `scheduler.js`.
- **Fix:** Define `buildWeeklyDigest()` in `scheduler.js`. It should call `getWeeklySummary()`, build the chart URL via `buildWeeklyChartUrl()`, and return `{ text: <formatted summary string>, chartUrl: <quickchart URL or null> }`. Export it in `module.exports`.

### 2. Fix `sendWhatsAppImage` export
- **Problem:** `sendWhatsAppImage` is defined in `scheduler.js:21` but not included in `module.exports` on line 255.
- **Fix:** Add `sendWhatsAppImage` to the `module.exports` object. Also add a `to` parameter (see #7).

### 3. Add Twilio webhook signature validation
- **Problem:** Anyone can POST to `/webhook` — no authentication.
- **Fix:** Add Express middleware using `twilio.webhook()` or manual `validateRequest()` before the webhook route. On validation failure, return 403 with no response body. Requires `TWILIO_AUTH_TOKEN` (already in env).
- **Implementation note:** Twilio signature validation requires the raw request body *before* Express parses it with `express.urlencoded()`. Capture the raw body via a custom middleware (`express.raw()` or `req.on('data')`) and store it on `req.rawBody` before the URL-encoded parser runs. Then validate against `req.rawBody`. This is ~30 lines, not a 5-line middleware addition.

### 4. Persist pending state via Google Sheets "Pending" tab
- **Problem:** `pendingCategory`, `pendingImport`, `pendingOnboarding`, `pendingContextual` are in-memory Maps. Server restart = lost state. Users mid-flow get no response.
- **Fix:** Create a new "Pending" sheet tab with columns: `Phone | Type | Data (JSON) | Created`. On each state write, upsert to Sheets. On each state read, check Sheets first, cache in Map. On delete, remove from both. Auto-expire entries older than 1 hour.
- **Race condition mitigation:** Add in-memory mutex per phone number. Lock at webhook entry, release after state write completes. This prevents concurrent webhooks for the same user from corrupting state, even on single server.
- **Sheets API read failure:** If read fails, clear in-memory cache and treat as empty state. Log error. If Pending sheet doesn't exist on startup, auto-create it with the schema.
- **Sheets API write failure:** Fall back to in-memory only and log a warning. Degrades gracefully — same behavior as today.

### 5. Dynamic salary cycle calculation
- **Problem:** `PAY_DATES_2026` array in `sheets.js:21-34` breaks January 2027.
- **Fix:** User setting (stored in Users sheet `salaryType`/`salaryDay` columns) takes precedence. If user has set `salaryType: 'fixed', salaryDay: 26`, calculate cycle bounds dynamically: for each month, pay date = salaryDay (or last day of month if salaryDay > days in month). Cycle runs from pay date of month N to (pay date - 1) of month N+1. `PAY_DATES_2026` becomes the fallback ONLY when no user setting exists. Add env var `DEFAULT_SALARY_DAY` (default: 28) for the no-user-setting case, replacing hardcoded arrays entirely.

### 6. Scrub `.env.example`
- **Problem:** `.env.example` contains real Google Sheet ID `1WepQlUmrK4NQ0UltaCZGTjRCHKP_ZRBSrIrTcl8ocT8`.
- **Fix:** Replace with `your_google_sheet_id_here`. Check git history — if the real ID was committed, rotate credentials (reshare sheet with new service account).

### 7. Fix multi-user messaging
- **Problem:** `sendWhatsApp(body)` in `scheduler.js` always sends to `YOUR_WHATSAPP_NUMBER` env var. When `server.js` calls `sendWhatsApp(text, from)`, the `from` param is silently ignored. Weekly chart delivery goes to wrong user.
- **Fix:** Refactor to two functions:
  - `sendWhatsAppTo(to, body)` — explicit recipient (for webhook replies)
  - `sendWhatsAppBroadcast(body)` — sends to all users (for scheduled nudges)
  - Remove the ambiguous `sendWhatsApp(body)` signature
  - Update all call sites in `server.js` and `scheduler.js`

### 8. Add test infrastructure
- **Framework:** Jest (standard for Node.js, zero-config)
- **Coverage targets by module:**
  - `parser.js`: Unit tests for `safeParseJSON`, `resolveMediaType`. Integration test with mocked Claude API for `parseExpense`.
  - `sheets.js`: Unit tests for `parseIndianDate`, `getISOWeek`, `buildProgressBar`, `parseSalaryInput`, `parseStatementInput`, `getBillingCycleAdvice`, `getSalaryCycleBounds`. Integration tests with mocked Google Sheets API for CRUD operations.
  - `server.js`: Integration test for webhook route with mocked Twilio/Claude/Sheets.
  - `scheduler.js`: Unit tests for `buildWeeklyChartUrl`, `getTopDiscretionaryCategory`.
  - `pdf-parser.js`: Unit tests for `deduplicateTransactions`.
  - `conversation.js`: Integration test with mocked Claude API.
- **Minimum target:** 80% line coverage on pure functions, at least 1 integration test per module.
- **Execution:** Run via `npm test`. Add `"test": "jest --coverage"` to package.json scripts. Add GitHub Actions workflow to run tests on push.

### 9. Deployment & Rollback Strategy
- **Deploy Phase 1 incrementally:** One fix at a time, verify after each. Tag each stable deployment (e.g., `v1.1.0-hardening`).
- **Rollback:** `git revert` + redeploy on Render. Keep `PAY_DATES_2026` fallback active for 2 weeks after salary cycle migration.
- **Health verification:** After each deploy, send a test message to the webhook and verify response.

### 10. Production Monitoring

- Prevents token burning from malicious or accidental oversized payloads.

## Phase 2: Feature Expansions (after Phase 1 is stable)

### 13. Logging streak tracker
- **Storage:** Add `currentStreak` and `longestStreak` columns to Users sheet.
- **Logic:** On each expense log, check if user logged yesterday. If yes, increment `currentStreak`. If no, reset to 1. Update `longestStreak` if exceeded.
- **Display:** Append streak to the logged-expense reply: "✅ Food Delivery · Swiggy ₹280 | 🔥 14-day streak!"
- **Milestones:** Send a special message at 3, 7, 14, 30, 60, 100 days. E.g., "🔥 7-day streak! You've been tracking every day for a week. Most people quit by day 3."
- **Edge case:** If user logs multiple expenses in a day, only count the streak once. If user logged yesterday, increment currentStreak. Otherwise, reset currentStreak to 1 (today's log starts a new streak). "Streak broken" note appears when streak goes from N>1 to 1.

### 14. Recurring expense auto-detection
- **Algorithm:** Group transactions from last 120 days by merchant name (normalize: lowercase, trim, remove special characters — exact match after normalization, not substring). For each merchant with 3+ transactions in this window, check if intervals between consecutive entries fall within 25-35 days. Amount must be within ±20% of median (e.g., if median is ₹500, accept ₹400-₹600).
- **Storage:** Add a "Recurring" sheet tab: `Merchant | Category | Avg Amount | Frequency | Last Seen | Confidence`.
- **Trigger:** Run detection weekly (Sunday 10 AM IST cron). Only surface new detections to user.
- **User flow:** "📋 Found 3 recurring expenses: Netflix ₹499/mo, Spotify ₹119/mo, Gym ₹2,500/mo. These add up to ₹3,118/mo in committed spending."
- **MVP scope:** Detection + notification only. No auto-categorization in v1. User can reply "ignore Netflix" to suppress future alerts.
- **Edge case — variable amounts:** Utility bills (electricity, water) may vary 50%+. Only flag as recurring if amount variance is ≤20% of median. Utilities with high variance get a softer label: "possible recurring."

### 15. Month-over-month comparison
- **Command syntax:** "compare march vs february", "compare last month", "march vs feb"
- **Parser intent:** `{"type": "compare_months", "month1": "march", "month2": "february"}` — add to parser.js SYSTEM_PROMPT.
- **Display format:**
  ```
  *March vs February*
  Total: ₹45,200 vs ₹38,900 (+16%)

  🛵 Food Delivery: ₹8,200 vs ₹6,100 (+34%) ⬆️
  🛒 Groceries: ₹5,800 vs ₹6,200 (-6%)
  🛍️ Shopping: ₹12,000 vs ₹4,200 (+186%) ⬆️
  ...
  ```
- **Edge case — incomplete month:** If current month is only 10 days in, note: "March (10 days so far) vs February (full month)."
- **Edge case — no data:** "Not enough data for March yet. Start logging!"

### 16. Smart categorization learning
- **Mechanism:** Track corrections via `edit_last` (action: edit category) and `bulk_recategorize`. Store in a "CategoryRules" sheet tab: `Merchant Pattern | Correct Category | Correction Count | Last Updated`.
- **Matching:** Before sending to Claude, check if merchant matches a learned rule. If `correction_count >= 3`, auto-apply the category and set confidence to 95. If `correction_count < 3`, include the rule as a hint in the Claude prompt: "Note: user has previously categorized [merchant] as [category]."
- **Conflict resolution:** If two rules conflict (same merchant, different categories), use the category with the highest `correction_count`. If tied, use most recently updated. This makes the system robust to single accidental miscategorizations.
- **Existing hardcoded rules:** The parser already has rules (CRED → Credit Card Payment, etc.). Learned rules take precedence over defaults.
- **Edge case:** User corrects "Swiggy" to "Groceries" (Swiggy Instamart) but also has "Swiggy" → "Food Delivery" entries. Solution: if the note/raw message contains "instamart" or "grocery", apply the Groceries rule; otherwise Food Delivery. For v1, just use the most recent correction.

### 17. Daily spending limit / allowance mode
- **Setup:** User says "set daily limit 1500" or "daily budget 2000". Parsed as `{"type": "set_daily_limit", "amount": 1500}`. Stored in Users sheet: `DailyLimit` column.
- **Display:** After each expense log: "✅ Lunch ₹280 — ₹1,220 left today (of ₹1,500)."
- **Calculation:** Sum today's discretionary expenses. Remaining = limit - today's total. Only counts discretionary categories (not committed like Rent, EMI).
- **Over-limit behavior:** Warning only, never blocks. "⚠️ Over daily limit by ₹340. You've spent ₹1,840 today (limit: ₹1,500)."
- **Reset:** Resets at midnight IST (00:00:00). Transactions timestamped >= 00:00:00 count toward the new day.
- **Over-limit messaging:** Warning shows on the first expense that exceeds the limit. Subsequent expenses show remaining as negative: "₹-340 remaining today."
- **Smart suggestion:** Only auto-suggest if monthly discretionary budget >= ₹15,000 (ensures daily limit of ₹500+). Formula: monthly discretionary budget ÷ days in month. If lower or no budgets set, prompt: "Set a daily spending limit to track your pace. Try: daily limit 1000".
- **Edge case:** Weekends may have higher spend. For v1, same limit every day. Could add weekend override later.

## Key Implementation Decisions
- **Pending state:** Google Sheets "Pending" tab (same infra, no new deps). Single-server assumption documented.
- **Salary cycle:** User setting overrides `PAY_DATES_2026`. Dynamic calculator for years without hardcoded arrays.
- **Test framework:** Jest with mocked external APIs.
- **Messaging refactor:** `sendWhatsAppTo(to, body)` replaces ambiguous `sendWhatsApp(body)`.
- **Twilio validation:** Requires raw body capture before `express.urlencoded()` runs (~30 lines, not 5).

## Risks
- **Google Sheets API rate limits:** Currently ~10 API calls per webhook request. Adding pending state persistence adds 1-2 more. Google Sheets API allows 300 requests/min — sufficient for single-user but would need caching for scale.
- **Recurring detection complexity:** Fuzzy merchant matching and interval detection are deceptively complex. MVP should be strict matching first, relax later.
- **Smart categorization cold start:** Requires correction history that doesn't exist yet. Feature only activates after user makes corrections.

## Eng Review Findings (14 issues resolved + 5 outside voice)

### Architecture (6 issues)
1. **Concurrency: Promise chain per user, not mutex.** Map<string, Promise> chains requests sequentially per phone number. ~10 lines. Same guarantee as mutex, less machinery.
2. **Messaging: Single shared module.** Create `messaging.js` with `sendWhatsAppTo(to, body)` + `sendWhatsAppBroadcast(body)`. Singleton Twilio client. All callers import from one place. Bundle with #1 and #2.
3. **Raw body: Use `verify` callback.** `express.urlencoded({ extended: false, verify: (req, res, buf) => { req.rawBody = buf.toString(); } })`. ~5 lines, not 30.
4. **Fix ordering: Bundle #1, #2, #7 as messaging refactor.** Do messaging module first. buildWeeklyDigest and sendWhatsAppImage land in new module cleanly.
5. **Cron collision: Stagger ALL 8 cron jobs with 30+ minute gaps.** Two collisions found: overspendCheck + eveningCheckIn at 8 PM, morningFollowUp + preStatementNudge at 9:05 AM. Plus smartNudge at 9:00 AM makes 3 messages in 5 minutes.
6. **PDF restart: Document as known limitation.** PDF processing is not resumable across restarts. User can re-send the PDF.

### Code Quality (5 issues)
7. **Hardcoded PII: Move to user profile.** conversation.js and pdf-parser.js have hardcoded personal info (Raagul, bank accounts, family names). Load from Users sheet with generic fallback.
8. **safeParseJSON crash: Fix + deduplicate.** Add outer try/catch returning `{ type: 'unknown' }`. Extract shared function. Currently crashes on bad Claude output.
9. **Budget cycle mismatch: Align getBudgetStatus() with salary cycle.** Currently uses calendar month while getMonthlySummary uses salary cycle. Numbers are incoherent.
10. **Double TwiML response: Add sent-check guard.** Track whether response was already sent. Outer catch only sends if flag is false.
11. **Auth reuse: Singleton Google auth + Sheets client.** Currently re-parsed from env var per call (10+ JSON.parse per webhook). Create once at module load, fail fast.

### Performance (1 issue)
13. **Request-scoped getAllRows() cache.** Cache per webhook request. ~15 lines. Cuts 2-4 redundant Sheets API calls per request, saving 40-60% latency.

### Outside Voice Findings (5 new issues)
15. **P0: Missing scheduler imports in server.js.** `scheduleEveningCheckIn`, `scheduleMorningFollowUp`, `scheduleLapseNudge`, `schedulePreStatementNudge` are called in `start()` but never imported. **App crashes on startup.** Fix first.
16. **Multi-user data layer: Add Phone column to Expenses.** Current Expenses sheet has no user column. All users see combined data. `undoLast()` deletes wrong user's expense. Add Phone column, filter `getAllRows()` by user.
17. **Pre-statement nudge month boundary bug.** `today.getDate() + 2` can equal 32. Use proper Date arithmetic.
18. **Second cron collision.** morningFollowUp and preStatementNudge share `'35 3 * * *'`. Covered by stagger-all fix (#5 above).
19. **Delete safety: Validate + confirm.** `deleteRowByIndex` trusts Claude's hallucinated rowIndex. Add range check + show what will be deleted + require user confirmation.
